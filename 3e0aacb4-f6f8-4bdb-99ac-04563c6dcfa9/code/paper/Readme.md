What "we have this Lean 4 proof" now means, formally. The release answers the question in two halves, both checked by the Lean kernel.

Which proof. tools/make_release_manifest.py pins the development by SHA-256: 93 source files (the Solana/vault/zkPoP modules plus the build pins lakefile.lean, lean-toolchain, lake-manifest.json), shipped as zkpop/artifact/zk-pop-solana-lean4-v1.manifest.sha256 (checkable with sha256sum -c) and as Lean data in the generated RequestProject/ReleaseManifestV1.lean. Lean then folds those digests and pins the root: releaseRoot_eq proves the fold equals the published root 0x5f21038acec49e38005dc301e313dddb; manifest_fileCount, manifest_paths_nodup and manifest_covers_headline_modules check the count, distinctness, and that the modules carrying the headline theorems are pinned. (The two files that are the release statement are excluded, since they cannot hash themselves; this is stated in the report.)

Possession, in zero knowledge. RequestProject/ZkPoPSolanaV1.lean instantiates the project's existing commit-and-prove argument at concrete numbers over ZMod 257, with a Fiat–Shamir hash offset by the manifest root, and publishes one certificate: commitment 163, announcements (23, 136), branch challenges (87, 91), responses (120, 200), branch statements (137, 12), recomputed challenge 178. Proved: releaseCert_numbers, releaseCert_public_data, releaseCert_equations (the verifier's equations at those numbers, by kernel computation), releaseCert_verifies (completeness), releaseCert_sound (any rewinding pair of certificates extracts a run certifying the public final account, hence the vault theorem — the run is never published), releaseCert_zero_knowledge and releaseCert_simulatable (the view is equal, not just indistinguishable, across the two certified runs, and equals a witness-free simulation), releaseCert_hides_the_run, and releaseHash_binds_root. zk_pop_solana_lean4_v1 conjoins the release in one statement.

Verification status. lake build completes for the whole project (8515 jobs, no errors); the new module contains no sorry. Its closing section runs every release theorem through the project's existing axiom gate, so the build fails if any of them ever depends on anything beyond propext, Classical.choice, Quot.sound — in particular on sorry or native_decide. tools/verify-release.sh reproduces the whole chain end to end (sha256sum -c, manifest regeneration diff, Lean build) and reports "verified".

What is assumed, and stated as such in the report: collision resistance of SHA-256 (so the root identifies the sources) and computational binding of the commitment (it is perfectly hiding here, so binding cannot also be unconditional). The concrete numbers run over the toy field ZMod 257 — an exhibition a reader can recheck by hand, not a security-parameter choice; all completeness, soundness and zero-knowledge theorems are proved for an arbitrary field, commitment module and hash.
